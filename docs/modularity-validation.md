## Implementation order

| Priority | Work and dependencies | Exit gate and principal risk |
| --- | --- | --- |
| 0. Baseline | Save a disposable copy of representative legacy data. Run the existing guided demo, browser/control suites and local measurements with pinned dependencies. Establish an append-only fixture and external-effect counter. | Reproduce existing behavior on the target host. Record environment, runtime SQLite library, browser version and known hostile-site limits. |
| 1. Registry and one swap | Use app assembly, plain factories and a locked mapping for a planner or read-only extractor. Wire the current implementation through it and add one alternative against the same contract. Keep Fake and Playwright paths working. | Change one binding, run the same workflow successfully with both, restore the original, and remove the alternate. No control bypass or stranded reference. The main risk is creating an abstraction that only mirrors one vendor API. |
| 2. Resumable chain | Add the smallest versioned workflow definition and persistence needed for a sequential flow, an independent fan-out and a conditional join. Reuse task groups, branch ownership, audits and the intent journal. Add one human wait only through existing control. | Demonstrate deterministic join and safe restart at each boundary. Replace a pinned implementation while a run waits for approval. The main risk is a split between committed state and in-memory scheduling or permission checks. |
| 3. External adapter | Select one real implementation that cannot run in the same environment or already exposes a protocol. Run a read-only capability in a restricted worker, using the same contract as the in-process alternative. | Pass handshake, cancellation, resource reclamation, uninstallation and negative-access tests. Measure warm and cold overhead. The main risk is counting a same-user child process as containment. |
| 4. Composition extensions | Add bounded runtime fan-out, child workflows or event starts when an identified chain needs them. Compare a wrapped specialist against the deterministic baseline. | Persist normalized expansions, preserve policy under cancellation, and show measurable outcome or operating benefit within matched budgets. |
| 5. Scale decision | Profile representative usage. Trial a durable engine only if a requirement such as cross-host failover or timers across process loss has been demonstrated. Run read-only work before pilot writes. | A candidate preserves journal, branch fencing, history and rollout semantics. The same workload and failure matrix show the required operational gain. |

Make stages 1 and 2 separately reversible. The first cut can run a binding and explicit Python composition without dynamic discovery, a generic graph interpreter, or a database schema change. For durable chains, add versioned workflow tables and a reviewed migration. `create_all` initializes missing objects in the current code. It does not upgrade existing schemas. Use additive migrations, fixtures from older releases and a read or export path for older histories. Preserve current HTTP endpoints and feature-gate admission of new chains until the gates pass. ## First vertical experiment

Use a seeded local invoice page and the existing workspace controller. The two extractor implementations accept the same bounded observation, return the same canonical fact and source reference, and require no browser write access. Start with two deliberately different implementations, for example a deterministic field extractor and a structured model-backed extractor over the same observed text. Use a deterministic provider stub for lifecycle and fault tests. Treat real model evaluation as a separate workload.

1. Run the workflow with A. Pause a second run after plan admission, before invocation, with its binding durably pinned.
2. Activate B. A third run must pick B, and the paused run must still use A when resumed. Compare typed results, durable traces and selected binding identities. Test both replacement directions.
3. Attempt to remove A while referenced. Verify the dependent workflow/run is listed and the artifact remains available. Drain the paused run or cancel it explicitly. Preserve its auditable terminal outcome.
4. Remove A. Restart. Current workflows resolve to B. Historical runs remain viewable and the removed code is absent from active resolution. Reject attempts to run an unresolved historical revision with a repairable error.
5. Repeat with a deliberately incompatible output schema, missing dependency, and failing startup check. The live generation must remain unchanged and continue serving existing definitions.

## Regression and fault matrix

| Area | Exercise | Pass condition |
| --- | --- | --- |
| Contract and data compatibility | Validate captured v1 inputs, outputs, JSON Schema fixtures and checkpoint round-trips. Try old optional fields, bad output, wrong major, changed permissions, missing package and cyclic dependencies. | Existing payloads remain readable. Incompatible plans are rejected before admission. Error codes identify the responsible capability and condition without exposing secret values. |
| Replace and remove | Change bindings while another run is in flight or waiting for review. Race admission against uninstall. Test orphaned workers, schedules, artifacts and credential grants after drain. | No double binding or silent migration. No enabled definition resolves to an absent capability. A run either completes under its original pin or reaches an explicit repairable or terminal state. History remains readable after uninstall. |
| Revocation and rollback | Revoke a plugin while queued, during planning, and after external dispatch. Restore the earlier compatible generation. Try incompatible checkpoint state, absent binary, and interrupted migration. | No new invocation after revocation. Admitted effects drain or become uncertain. Rollback preserves old state and refuses unreadable formats. Startup can safely retry interrupted additive migration. |
| Workflow correctness | Seed conditional branches, empty fan-outs, independent failures, bounded dynamic expansion, duplicate event starts, nested budgets, reducer order and crash after commit before scheduling. | Selected nodes run once logically, joins are deterministic, a duplicate event produces one run, and restart finds committed ready work. Missing optional nodes resolve through declared skip behavior. |
| Cancellation and approval | Cancel before and after claim, while queued for inference, during a human wait, and after command admission. Race edit, approval, takeover, resume and stale worker result against the same revision. | No new work after cancellation. A browser command either drains to a recorded outcome or becomes uncertain. Stale approvals and attempts cannot authorize a dispatch. User takeover remains exclusive and responsive. |
| Effect durability | Inject faults before intent commit, after commit before dispatch, after fixture effect before result commit, and after result commit before successor scheduling. Exercise provider idempotency and mismatched payload rejection. | Proven undispatched safe work may resume. An unresolved recorded intent requires reconciliation. A confirmed result settles without replay. The fixture observes zero unapproved effects and zero duplicate irreversible effects under every injected failure. |
| Isolation and security | In an isolated fixture, try filesystem traversal, credential and database reads, cross-run artifact use, denied destination and redirect, fork bomb/resource abuse, and malformed or oversized protocol messages. Include misleading page and tool metadata. | Access is denied by an enforced boundary. One worker crash cannot take down core or a sibling. Deadlines terminate the child tree, quotas remain enforceable, and secrets or raw page data do not enter diagnostics. |
| State portability | Export and reimport legacy and new run history, retained checkpoints and owned artifacts through a supported path. Run a fixture against a prospective alternate state adapter. | Restore IDs, order, schema versions and namespace semantics. Results preserve redaction, atomic run/step transitions and effect uncertainty. |
| Backpressure and operations | Saturate model, browser, CPU and stream capacity separately. Stop a worker with a full queue. Disconnect SSE and reconnect through snapshot plus history. | Bounded memory, fair progress, explicit queue-full or wait responses, recoverable final output, and no leaked permits or hung children. Durable audit works with telemetry disabled. |

Use the existing approval, control, recovery, security, browser workspace and task-group tests as gates throughout. Use fixtures with deterministic barriers rather than sleeps to place faults precisely. Run a dedicated worker isolation suite on each supported operating system and profile. The known hostile authenticated page and redirect scenarios need a separate browser security design and acceptance before broader deployment. ## Performance experiment

Define the thresholds below before collecting the comparison. They are proposed decision gates for the local deployment and can be adjusted after the baseline exposes actual operating constraints. Measure direct built-in execution, then the registry-backed path, then the same capability across a worker boundary. Compare identical fixtures, payloads, approved destinations, model weights, context and budgets. Interleave trials after warm-up, report cold starts separately, and keep deterministic test inference separate from real model variability.

| Workload | Measurements | Proposed decision gate |
| --- | --- | --- |
| Lightweight typed calls | Median and p95 wall time and CPU over at least 1,000 calls per variant. Include small and maximum supported payloads and worker startup/teardown. | Added p95 under 1 ms for a warm in-process call on the small fixture. Budget worker overhead against each capability. Prefer a local call for trivial work if transport or startup dominates. |
| Interactive Chromium | At least 30 measured trials per variant at idle and intended concurrent load. Measure input-to-visible p95, takeover p95, and completed verified tasks. Record total process-tree working set. | Stay within the existing 500 ms local p95 input-to-visible target and within 10% of matched baseline p95 for takeover. Treat a baseline miss as a reason to profile before increasing parallelism. |
| Parallel fan-out | Sweep concurrency 1, 2 and 4 for independent I/O with identical work. Compare shared model slot and separate available slots, and run same-branch actions serially. Record makespan, tail delay, retries, SQLite busy time, memory and completion rate. | Enable higher concurrency only where median makespan improves at least 20% on that workload while the same correctness, responsiveness and configured memory limits pass. |
| Saturation and soak | Hold the expected operating load for at least one hour, then release all resources. Sample queues, open handles, children, file/profile growth, SQLite write latency and resource return. | Queues remain bounded and drain. No sustained growth across repeated steady-state windows, no retained child process or leaked slot, and no lost journal outcome. |
| Independent specialists | Hold out browser tasks, including missing evidence and misleading content. Compare deterministic logic, a single agent, and bounded collaboration with identical action, cost and wall-time budgets. | Use collaboration only where it improves verified task outcomes or evidence quality without weakening approval and isolation gates. Report sample sizes and the paired task results. |

The workspace's prior measurements cover small local browser and model workloads. The plugin dossier's stdio microbenchmark isolates transport and scheduling overhead under a trivial workload. It cannot estimate security enforcement, browser memory, framework latency or model throughput. [Workspace measurements](optimization.md), [Transport probe](modularity-plugin-evidence.md)

## Extension review record

For each accepted implementation, record its owner, source and artifact pin, supported contract versions, execution profile, licenses and notices, permissions, known weaknesses, state owner, removal procedure and observed validation results. Record the exact fixtures and environment for a reviewed correction. Reuse the same compatibility suite against a replacement before approving it. Keep evaluation examples separate from tuning examples. When a candidate becomes unsupported, freeze admissions of vulnerable or incompatible versions, drain or revoke based on risk, and use the retained state export to move supported runs.
