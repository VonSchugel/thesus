# THESUS workflow engine evidence

Reviewed November 6, 2026. This comparison assumes the current single-process FastAPI deployment with a local SQLite database, branch-scoped Chromium profiles, and optional local or hosted inference. It treats the approved browser command boundary as part of the product contract. Release dates below are GitHub publication dates in UTC. Code references point to the releases inspected. Documentation describes intended behavior. Deployments and research are labeled separately. Integration fit and expected costs are THESUS judgments. The engines were evaluated from source and documentation, with no cross-engine benchmark or fault-injection run for this report. [Workspace operating model](../README.md#operate-and-test), [workspace architecture](../ARCHITECTURE.md)

## Decision at the current scale

Keep the local branch runner and workspace persistence. Add typed workflow composition at the application boundary, starting with deterministic sequences and a bounded parallel join. The existing `ExecutionManager` coalesces work by `(session_id, branch_id)` and drains tasks on shutdown. `TaskGroups.create` commits group members before scheduling them. `LiveWorkspace` keeps model requests under a shared semaphore and validates browser revisions and approvals before dispatch. The current restart path interrupts active runs and requires explicit resume. These are useful product semantics that a new engine would have to preserve. [Branch scheduler](../app/core/execution_manager.py#L8), [task groups](../app/core/task_groups.py#L30), [live browser dispatch](../app/core/live_workspace.py#L505), [startup recovery](../app/core/recovery.py#L12)

The decision changes if THESUS needs restartable graph-owned state for several complex workflows or automatic multi-host recovery. Trial LangGraph for the first need and Temporal for the second. Trial DBOS alongside Temporal when owning a separate workflow service would dominate the cost. Use OpenAI Agents SDK for a scoped specialist and Prefect for a scheduled batch workflow if those use cases arise.

## What the implementations actually provide

### Local execution with structured concurrency

`TaskGroup` cancels sibling tasks when one raises an unexpected exception and waits for cleanup. That behavior suits a fail-fast join. For independent group members, turn expected failures into typed results at each child boundary and keep cancellation available for a stop request. Limit ready work as well as active work. A semaphore caps active calls, while a bounded `asyncio.Queue` can apply backpressure to producers. A thread pool can host trusted blocking I/O, but cancelling the awaiting coroutine does not stop a running thread. Use a restricted process when a hard resource or trust boundary is required. On the same browser branch, preserve one mutating writer. [Task group cancellation](https://docs.python.org/3.12/library/asyncio-task.html#task-groups), [bounded queues](https://docs.python.org/3.12/library/asyncio-queue.html), [future cancellation](https://docs.python.org/3.12/library/concurrent.futures.html#concurrent.futures.Future.cancel)

The existing multitask report measured about 24% shorter median completion for paired CPU inference using two model slots, at roughly 226 MiB more peak model working set. The small, ordered sample used one model. It motivates a capacity trial for overlapping calls and gives no framework overhead or browser-quality estimate. Keep one inference slot initially and run independent branches concurrently only within browser, model and queue limits. [Local capacity measurement](multitask-research.md#local-inference-capacity-check)

### LangGraph

**Source and docs.** `StateGraph` registers code-defined nodes, edges and channels, and `compile` validates the topology and takes a checkpointer. Nodes publish state deltas. A reducer combines concurrent updates for a state key. `Send` adds inputs for dynamic fan-out and subgraphs can encapsulate a chain. `PregelRunner.commit` persists task writes, while `_reapply_writes_to_succeeded_nodes` recovers successful sibling writes. With a durable checkpointer and a thread identity, `interrupt` parks execution and `Command(resume=...)` supplies a response. The node starts again from its beginning. Node names, channel schemas and checkpoint dependencies need version handling for resumed runs. [Graph builder and compile](https://github.com/langchain-ai/langgraph/blob/1.2.20/libs/langgraph/langgraph/graph/state.py#L1177), [runner commit](https://github.com/langchain-ai/langgraph/blob/1.2.20/libs/langgraph/langgraph/pregel/_runner.py#L575), [recovery loop](https://github.com/langchain-ai/langgraph/blob/1.2.20/libs/langgraph/langgraph/pregel/_loop.py#L835), [interrupt implementation](https://github.com/langchain-ai/langgraph/blob/1.2.20/libs/langgraph/langgraph/types.py#L913), [graph API](https://docs.langchain.com/oss/python/langgraph/graph-api), [persistence](https://docs.langchain.com/oss/python/langgraph/persistence)

**Fit.** Adapt state snapshots, reducers and graph namespaces before bringing in the runtime. If a trial warrants a dependency, put model or pure-data planning inside the graph and return a typed proposal to THESUS. A second checkpoint store for the same approval or browser action creates a crash window between the stores. Define an authoritative dispatch ledger and pin node, capability, schema and workflow versions before enabling durable use. On removal, drain graph-owned runs or export an explicitly supported checkpoint, then start new runs using the local runner. [Interrupt constraints](https://docs.langchain.com/oss/python/langgraph/interrupts), [deployment compatibility](https://docs.langchain.com/oss/python/langgraph/backward-compatibility)

### OpenAI Agents SDK

**Source and docs.** The host constructs an `Agent` with a model, instruction, tool and handoff list. `Runner` drives the agent loop. `Agent.as_tool` makes a specialist callable under a manager, while a handoff delegates ownership of the next response. `RunState` carries resumable tool interruptions and the approval record. For custom functions, human review can be configured on the function tool. Input and output guardrails apply at the entry and final-agent boundaries, and per-tool validation belongs alongside the individual effect. SDK sessions and serializable state supply continuation mechanisms that the host can persist. [Agent as tool](https://github.com/openai/openai-agents-python/blob/v0.24.0/src/agents/agent.py#L606), [runner](https://github.com/openai/openai-agents-python/blob/v0.24.0/src/agents/run.py#L279), [run state](https://github.com/openai/openai-agents-python/blob/v0.24.0/src/agents/run_state.py#L842), [SDK ownership](https://developers.openai.com/api/docs/guides/agents/sdk), [guardrails and review](https://developers.openai.com/api/docs/guides/agents/guardrails-approvals)

**Fit.** Map its input and final structured result onto an independently replaceable THESUS specialist. The browser capability should accept a validated command from THESUS after its existing review, so the specialist sees read-only evidence or returns a proposed action. Pin provider, model and SDK versions for runs. Audit provider support for structured output and tools using the local endpoint actually deployed. Keep credentials and serialization scoped to the adapter and configure trace export to prevent page or tool data from leaving the workspace unexpectedly. [Models and providers](https://developers.openai.com/api/docs/guides/agents/models), [integrations and observability](https://developers.openai.com/api/docs/guides/agents/integrations-observability)

### Pydantic AI

The pinned backend guide separates an operation's stable identity from its persisted name and distinguishes callable submission from early worker registration. It also shows why adapter contracts need explicit results. The Temporal integration reconstructs a copy of agent context inside an activity, so delegated usage accumulated through mutation can disappear from the parent. In-process DBOS or Prefect can preserve the mutation on a fresh call, yet replay or a cached result can skip the call. Make token usage and other accounting explicit results, persist them once by operation identity, and enforce a budget at the host. The November 4 release notes also disclose fixes for attacker-influenced web-fetch memory growth and separate harness redaction work that can block the event loop. A trusted agent library can still accept untrusted data. Keep such features scoped to the adapter and evaluate exact pins and selected extras. [Pinned backend guide](https://github.com/pydantic/pydantic-ai/blob/v2.66.0/docs/durable_execution/backends.md#L23-L41), [pinned context semantics](https://github.com/pydantic/pydantic-ai/blob/v2.66.0/docs/durable_execution/temporal.md#L219-L237), [delegated usage issue](https://github.com/pydantic/pydantic-ai/issues/6886), [release advisories](https://github.com/pydantic/pydantic-ai/releases/tag/v2.66.0)

### Temporal

**Source and docs.** The worker runs deterministic workflow code from recorded event history. Workflow definitions call separately registered activities for model requests, browser commands and other I/O. Child workflows support nested jobs. Signals and Updates drive durable external input. The Python worker handles workflow activations, schedules activities, and handles cancellation on the activity worker. Heartbeats and cancellation modes are application choices. `Replayer` tests new code against saved histories, and Worker Versioning can route pinned executions to compatible versions. The workflow sandbox constrains nondeterministic code. Contain untrusted code with an operating-system boundary. [Workflow activation](https://github.com/temporalio/sdk-python/blob/1.35.0/temporalio/worker/_workflow_instance.py#L453), [activity cancellation](https://github.com/temporalio/sdk-python/blob/1.35.0/temporalio/worker/_activity.py#L219), [activity options](https://github.com/temporalio/sdk-python/blob/1.35.0/temporalio/workflow/_activities.py#L72), [replayer](https://github.com/temporalio/sdk-python/blob/1.35.0/temporalio/worker/_replayer.py#L38), [Python workflows](https://docs.temporal.io/develop/python/workflows), [worker versioning](https://docs.temporal.io/worker-versioning), [sandbox constraints](https://docs.temporal.io/develop/python/best-practices/python-sdk-sandbox)

**Fit.** Transfer one read-only chain first. Persist typed completion events and approval requests through THESUS and use a run ID to correlate engine history. Route browser activities to the owner of the live browser lease. A durable workflow can recover while a browser context or authenticated profile is unavailable. When no live owner exists, use explicit restore and observation or stop for reconciliation. An activity with an uncertain browser mutation requires a stable intent ID and reconciliation. Heartbeats, queue deadlines, and a cancellation result cannot prove an external effect stopped. A reported SDK cancellation race with a reproducer was closed as not planned on October 28, 2026. Use it as a regression case on the chosen SDK. [Activity idempotency](https://docs.temporal.io/activity-definition#idempotency), [Python cancellation report](https://github.com/temporalio/sdk-python/issues/700)

### DBOS Transact

**Source and docs.** Workflow and step decorators wire ordinary Python functions into the embedded runtime. `_core.workflow_wrapper` binds workflow execution, and `record_step_result` persists outputs for subsequent deterministic replay. The runtime uses its own system database. The default SQLite backend is suitable for a local trial, while the documentation recommends Postgres for production. A recovered workflow reruns from its beginning using recorded step results, then executes at the first missing result. Application-version routing can preserve workflow code compatibility. High availability across hosts also needs coordinated recovery. DBOS recommends its Conductor for that role. [Workflow wrapper](https://github.com/dbos-inc/dbos-transact-py/blob/3.4.0/dbos/_core.py#L1979), [step recording](https://github.com/dbos-inc/dbos-transact-py/blob/3.4.0/dbos/_core.py#L2455), [architecture and recovery](https://docs.dbos.dev/architecture), [database and versions](https://docs.dbos.dev/python/tutorials/database-connection/)

**Fit.** Use a separate database in a trial and wrap one versioned execution entry point. Route non-deterministic work through steps and test loss after a browser effect but before the step result write. A host restart that repeats a step can still duplicate an external effect without idempotency or reconciliation. Preserve the native THESUS run record and validate upgrading and draining the workflow database. Version 3.0 split stored workflow inputs and outputs into new tables and removed legacy APIs, so test rollback with a copy of retained workflow data. Compare operational recovery, incident tooling and workflow latency to Temporal before choosing it for multi-host use. [Step semantics](https://docs.dbos.dev/python/tutorials/step-tutorial), [3.0 schema and API changes](https://github.com/dbos-inc/dbos-transact-py/releases/tag/3.0.0)

### Prefect

**Source and docs.** `TaskRunner` defines task submission and `ThreadPoolTaskRunner`, `ProcessPoolTaskRunner` and `PrefectTaskRunner` provide local or distributed execution strategies. `@flow` and `@task` construct the dependency model through parameters and futures. The task engine tracks attempts, terminal state and transactional result handling. A deployment can use work-pool configuration and workers for scheduling and infrastructure. Persistence is configurable. Cancellation of a deployed flow needs a worker to locate and stop its infrastructure. An already running thread can finish after a cancellation request. [Runner source](https://github.com/PrefectHQ/prefect/blob/3.9.1/src/prefect/task_runners.py#L243), [process runner](https://github.com/PrefectHQ/prefect/blob/3.9.1/src/prefect/task_runners.py#L760), [task engine](https://github.com/PrefectHQ/prefect/blob/3.9.1/src/prefect/task_engine.py#L1001), [result persistence](https://www.prefect.io/docs/v3/advanced/results), [deployment cancellation](https://www.prefect.io/docs/v3/advanced/cancel-workflows)

**Fit.** Adapt an isolated batch such as extracting metadata from completed runs or exporting sanitized replay records on a schedule. Keep batch-specific state outside the browser lease path. Take the task runner and result-store concepts if those jobs are simple enough for the local runner. Trial a deployment only when scheduling, independent operation and run visibility offset the additional control plane.

## Forks, compatibility projects, and deployment evidence

- **Cadence and Temporal, mature fork.** The Temporal project and Cadence maintainers both document the fork's origin in Uber's Cadence. Cadence has an independent active release line with `v1.4.5` published October 30, 2026. Uber's own engineering report documents use at large scale and replay or shadow testing. That scale is author-reported and its deployment differs from THESUS. The durable workflow and activity split is portable as a design. Treat the two implementations as separate integration targets and verify the needed worker SDK, operational tooling and migration before considering a switch. [Temporal origin](https://github.com/temporalio/temporal/blob/v1.32.2/README.md), [Cadence maintainers' comparison](https://cadenceworkflow.io/faq/cadence-vs-temporal/), [Cadence release](https://github.com/cadence-workflow/cadence/releases/tag/v1.4.5), [Uber deployment report](https://www.uber.com/us/en/blog/announcing-cadence/)
- **Pi Temporal, recent fork-backed adapter.** `pi-temporal` v0.2.0 was published October 9, 2026. It uses a small fork that exposes model, tool and sealing phases in Pi's `AgentSession`, with an external turn executor and a session write guard. The pinned source shows one attempt for a host-affine tool call, a separate dispatch claim, and a fence checked before session writes. The file fence has a check-to-append window, and stopping stale transcript writes cannot revoke effects on another service. THESUS should use a conditional write for its own durable fence and keep its browser effect reconciliation. The authors' proposed upstream order is instructive. Put a reusable write guard and lifecycle hook upstream, while retaining engine-specific policy in the adapter. The project's demo and the maintainers' report establish a working integration to inspect, with no independent production maturity claim. [Release](https://github.com/temporalio/pi-temporal/releases/tag/v0.2.0), [host queue and retry policy](https://github.com/temporalio/pi-temporal/blob/057c43dc4cdcf0af3cf6989f7e61af4caf3e537f/src/core/workflow.ts#L147-L189), [dispatch claim](https://github.com/temporalio/pi-temporal/blob/057c43dc4cdcf0af3cf6989f7e61af4caf3e537f/src/core/pending.ts#L44), [fence tradeoff](https://github.com/temporalio/pi-temporal/blob/057c43dc4cdcf0af3cf6989f7e61af4caf3e537f/src/core/fence.ts#L1-L20), [upstream patch plan](https://github.com/temporalio/pi-temporal/blob/057c43dc4cdcf0af3cf6989f7e61af4caf3e537f/docs/upstream.md), [maintainer demo report](https://temporal.io/blog/the-immortal-life-of-pi-running-the-pi-coding-agent-on-temporal)
- **DBOSify, compatibility shim.** Version `0.4.0` published June 24, 2026. It provides a subset of the Temporal Python API over DBOS and Postgres. The documented exceptions include gRPC compatibility, offline JSON history replay and process-pool activities. Closed-workflow queries need a worker running current registered code, and signal and cancellation behavior differs. Source-compatible calls can still change recovery and operations. Prefer THESUS-owned contracts over an engine-compatible import shim. [Release](https://github.com/dbos-inc/dbosify-py/releases/tag/0.4.0), [pinned compatibility limits](https://github.com/dbos-inc/dbosify-py/blob/0.4.0/docs/ARCHITECTURE.md#L9-L101)
- **Pi Durable, emerging design.** Earendil describes an experimental harness with typed documents committed with the transcript, configurable fork inheritance, and per-call replacement by registry name. Its next call can pick up new code while the prior call finishes on the old code. That design favors rapid iteration. A THESUS browser run with pending approval instead needs the precise capability and policy versions to remain pinned. Adopt coherent state and transcript commits and explicit fork policies. Choose new bindings at a declared checkpoint or at new-run creation. The Hacker News launch thread is useful for identifying packaging and extension concerns, with no operational guarantees implied by comments. [Maintainer announcement](https://earendil.com/posts/pi-durable/), [launch discussion](https://news.ycombinator.com/item?id=49925969)
- **Practitioner deployments and prototypes.** Grid Dynamics engineers describe refactoring a shared-state LangGraph research agent into explicit Temporal activities to improve testability and recovery. The account is hosted by Temporal and the implementation changes confound a framework-only comparison. Elastic's LangGraph demo illustrates bounded quality-check loops with Elasticsearch and a local model. A Temporal case study describes Replit migrating its agent control plane to Temporal Cloud. The deployment speaks to cross-worker scale, while costs for a single Windows workstation require a local trial. [Grid Dynamics migration](https://temporal.io/blog/prototype-to-prod-ready-agentic-ai-grid-dynamics), [Elastic demonstration](https://www.elastic.co/search-labs/blog/multi-agent-system-llm-agents-elasticsearch-langgraph), [Replit case study](https://temporal.io/resources/case-studies/replit-uses-temporal-to-power-replit-agent-reliably-at-scale)
- **Research checks.** The *Resume Means Resume* preprint uses a model-checked contract and pinned deterministic fault injection. Its reported crash and concurrent-resume findings include LangGraph `1.2.9`, older than the inspected `1.2.20`. Re-run the scenarios on the selected version. *BEGIN AI TRANSACTION* audits popular LangGraph repositories and identifies semantic version drift as a separate problem from persistence. That motivates recording the specific tool, prompt and model bindings used by a run. The preprints' results are author-reported and supply hypotheses and test cases for THESUS. ## Trial gates

1. **Compare the same chain.** Use deterministic fake browser and model fixtures for a sequence, branch, parallel join, nested read-only chain, approval and one injected post-dispatch failure. Feed identical inputs and budgets into the local runner and one candidate. Compare step outcomes, event ordering and state transitions. Preserve task-group, approval, recovery and replay tests as regression coverage. [Existing task-group tests](../tests/test_task_groups.py), [existing crash tests](../tests/test_adversarial_recovery.py#L259)
2. **Exercise recovery boundaries.** Kill a worker before intent persistence, after persistence but before dispatch, after the effect but before completion persistence, and after completion. Repeat a resume concurrently and make an old worker return after a new lease is issued. Require one accepted approval decision, zero duplicate browser mutations, no stale result publication, and a visible unknown-outcome state when the destination cannot prove success. Force a version switch while awaiting approval and require that the original implementation resumes or an explicit migration or cancellation is recorded.
3. **Measure cost and contention.** Measure warm and cold p50 and p95 end-to-end latency, queue time, engine-only latency with stubbed I/O, restart recovery time, peak process memory, database writes and token use. Use fan-out of one, two and four on the same host, with fixed browser and model capacity. Repeat with real local inference and the guided demo before accepting a change. Establish the acceptable overhead and availability target before comparing results. Keep separate measurements for local and multi-host configurations.
4. **Prove removal.** Start only new runs on the candidate while legacy runs continue locally. Disable the candidate for new runs, drain active runs, and start an equivalent workflow on the local runner. Reopen prior history with the dependency absent and inspect its event timeline. Keep original replay data with the applicable retention policy. Import in-flight work only at an explicitly supported stable checkpoint, with recorded state and a validated authority transfer. A paused approval or uncertain browser outcome requires its original runner or explicit reconciliation.
