# THESUS plugin and isolation evidence

Research snapshot for 6 November 2026. Source observations below identify released code, documentation records vendor commitments, and community reports describe individual experiences. The only new measurements are the local transport probe at the end. Release recency is an activity signal. Deployment maturity is assessed separately from release recency.

## Comparison for a local browser workspace

| Option | Selection and composition | Replacement and removal | Runtime and operational cost | Security and compatibility | THESUS decision |
|---|---|---|---|---|---|
| Explicit Python factory map with optional PyPA entry points | Select one implementation per slot. Compose in the host. Installed wheels can advertise named factories. | Change a binding for new work. Drain old handles. Restart to replace imported code or shared dependencies. | Lowest effort and call overhead. Requires an environment lock and explicit lifecycle ownership. | Python-only API. Every imported module shares host authority. | Adopt the factory map. Add allowlisted discovery once an independently distributed Python adapter needs it. |
| Pluggy | Registered implementations extend named hooks through specs, wrappers, ordering, and optional first-result selection. | Unregister removes dispatch entries. Host still owns resources and package dependencies. | Low call overhead. Hook semantics add cognitive and testing cost. | Shared Python process. Hookspec checks cover signatures and hook rules. | Defer until a concrete multi-subscriber extension point needs these semantics. |
| Stevedore | Named drivers and extension sets over entry points, with manager classes and load callbacks. | Manager can select a driver or rebuild a set. The application manages live instances and resources. | Low per-call overhead. More infrastructure than a small explicit registry. | Shared Python process. The enabled manager can run imports before its filter. | Reuse the named-driver pattern. Keep authorization ahead of import in THESUS. |
| Supervised local process, informed by go-plugin and OpenTofu | Discover an installed artifact through its manifest. Negotiate a narrow language-neutral contract at worker start. | Run compatible versions in parallel environments. Route new work to the staged worker and retain old worker leases as needed. | Serialization, process startup and resident memory. Cross-platform cleanup and diagnostics require work. | Separate address space and dependencies. Restrict OS authority separately. Version and validate the wire protocol. | Prototype for the first incompatible dependency, blocking native library, or independently crashable implementation. |
| Dapr sidecar and pluggable components | Declarative named state, event, secret and other adapters with standardized APIs. | Config updates can close and reinitialize a component. Data migration remains application-specific. | Sidecar plus the backing component or service. Adds deployment and network operations. | Language-neutral APIs. Native Windows pluggable-component discovery is skipped in the reviewed release. | Defer. Use a bounded Dapr adapter if a deployment already uses it and needs several building blocks. |
| Wasmtime with WASI/WIT | A typed component imports an explicit set of host interfaces and exports selected operations. | Load a separate instance and transfer only documented state. Keep artifact and working state independently addressable. | Runtime embedding, guest toolchain, compilation, and host-call mediation. | Portable within supported bindings and WASI versions. Security depends on host imports, limits, and runtime patching. | Evaluate for portable pure transforms when there are real third-party authors. |

## Python discovery and extension dispatch

**PyPA entry points and CPython.** The packaging specification separates the group, name, and importable object reference. On Python 3.12, `entry_points(group=...)` enumerates installed metadata and `EntryPoint.load()` resolves the object by importing its module. Conflict resolution is the consumer's responsibility. Package installers resolve Python requirements for the target environment. THESUS remains responsible for runtime capability dependency resolution and lifecycle management. Verify distribution name, version, locked artifact digest, unique entry-point name, and allowed target from non-executable metadata before `load()`. Validate the config and run a readiness check before the host publishes the factory. Ship a separate environment and process if libraries have incompatible transitive requirements. [PyPA specification](https://packaging.python.org/en/latest/specifications/entry-points/), [Python 3.12 metadata API](https://docs.python.org/3.12/library/importlib.metadata.html#entry-points), [CPython implementation](https://github.com/python/cpython/blob/v3.12.14/Lib/importlib/metadata/__init__.py), [pip hash checking](https://pip.pypa.io/en/stable/topics/secure-installs/)

**Pluggy 1.7.0, MIT.** The maintainer changelog dates the release to 14 October 2026 and PyPI records the wheel upload and provenance on 15 October. In the attested commit, `PluginManager.register` stages hook validation, `_verify_hook` checks declared arguments and hook rules, `load_setuptools_entrypoints` selects installed candidates by group and optional name, and `unregister` drops the manager's hook associations. The pytest ecosystem is a mature example of an extensible host that intends to call multiple listeners. THESUS's browser and model slots each choose an implementation. A general hook fan-out adds behavior beyond that need. Registration and unregistration bugs fixed in 1.7.0 are concrete examples of testing failed registration and ambiguous removal. Import-time side effects, background tasks and durable state belong to a different lifecycle. [PyPI 1.7.0 and attestation](https://pypi.org/project/pluggy/1.7.0/), [pinned manager](https://github.com/pytest-dev/pluggy/blob/4c7f6365f2dde09c11e72db67d0f615231d64c19/src/pluggy/_manager.py#L185), [license](https://github.com/pytest-dev/pluggy/blob/4c7f6365f2dde09c11e72db67d0f615231d64c19/LICENSE), [pytest extension discovery](https://docs.pytest.org/en/stable/how-to/writing_plugins.html#plugin-discovery-order-at-tool-startup), [registration issue](https://github.com/pytest-dev/pluggy/issues/733), [unregistration fix](https://github.com/pytest-dev/pluggy/pull/759)

**Stevedore 5.9.1, Apache-2.0.** The 20 August 2026 PyPI upload and OpenStack Hibiscus release mapping identify commit `44e1028`. `ExtensionManager.list_entry_points` discovers metadata, `_load_plugins` handles loading failures through callback or logging paths, and `_load_one_plugin` resolves the entry point and optionally constructs the object. `DriverManager` enforces a single matching driver. `EnabledExtensionManager._load_one_plugin` delegates to the base loader before running `check_func`, so the filter cannot prevent import-time execution. Use the pattern of a stable named slot with one selected driver. Perform THESUS allowlist checks on the candidate's identity before loading code. [PyPI release](https://pypi.org/project/stevedore/5.9.1/), [OpenStack release mapping](https://releases.openstack.org/hibiscus/), [extension loader](https://github.com/openstack/stevedore/blob/44e1028b014a73d00ef31251a10cb08cd989e8a6/stevedore/extension.py#L275-L348), [single driver validation](https://github.com/openstack/stevedore/blob/44e1028b014a73d00ef31251a10cb08cd989e8a6/stevedore/driver.py#L155), [enabled filter](https://github.com/openstack/stevedore/blob/44e1028b014a73d00ef31251a10cb08cd989e8a6/stevedore/enabled.py#L90-L103), [license](https://github.com/openstack/stevedore/blob/44e1028b014a73d00ef31251a10cb08cd989e8a6/LICENSE)

## Process plugins and a production fork

**HashiCorp go-plugin v1.8.0, MPL-2.0, released 29 April 2026.** `ClientConfig` accepts a child command or a reattachment configuration and supports `VersionedPlugins`. `Client.Start` launches and reads the startup handshake, and `checkProtoVersion` validates the offered version. `Client.Kill` owns stop and cleanup behavior. Optional `SecureConfig.Check` compares the binary against an expected checksum. Use a trusted checksum source and a staging path the worker cannot modify. The server explicitly describes the magic cookie as a user-experience feature. Optional AutoMTLS protects the compatible RPC connection. Go-plugin leaves package discovery, signing policy, application state, retries and OS permissions to the caller. Transfer typed handshake, bounded startup, exit monitoring, separate stderr, and explicit stop ownership. For the first Python worker, use one transport owned by the existing host. [Release](https://github.com/hashicorp/go-plugin/releases/tag/v1.8.0), [client configuration and integrity](https://github.com/hashicorp/go-plugin/blob/v1.8.0/client.go#L142), [start](https://github.com/hashicorp/go-plugin/blob/v1.8.0/client.go#L580), [stop](https://github.com/hashicorp/go-plugin/blob/v1.8.0/client.go#L498), [server handshake](https://github.com/hashicorp/go-plugin/blob/v1.8.0/server.go#L41-L55), [license](https://github.com/hashicorp/go-plugin/blob/v1.8.0/LICENSE)

**OpenTofu v1.13.9, MPL-2.0, released 5 November 2026.** This production Terraform fork separates provider requirements, dependency locks and artifact installation from runtime RPC. `Installer.EnsureProviderVersions` works on a copy of the lock, reconciles requirements with available packages, and reports per-provider failures. `providerFactory` opens the cached binary through go-plugin, and `initializeProviderInstance` selects the protocol 5 or 6 wrapper and retains the child handle. The fork operates its own registry and can resolve separately distributed providers through the inherited registry and provider protocol approach. The fork's compatibility promise covers the version 5 provider protocol throughout v1.x. Its migration documentation treats persistent state and new features separately. Its signing documentation also identifies weaker cases, including manually installed binaries and an option to skip GPG validation for certain default-registry packages. The design lesson is to keep contract version, artifact identity, and persisted data schema distinct. Validate equivalent operations and reversible data migrations independently of wire compatibility. [Release](https://github.com/opentofu/opentofu/releases/tag/v1.13.9), [installer](https://github.com/opentofu/opentofu/blob/v1.13.9/internal/providercache/installer.go), [runtime provider factory](https://github.com/opentofu/opentofu/blob/v1.13.9/internal/command/meta_providers.go#L355-L425), [registry engineering writeup](https://opentofu.org/blog/building-the-opentofu-registry/), [compatibility policy](https://opentofu.org/docs/language/v1-compatibility-promises/), [migration guides](https://opentofu.org/docs/intro/migration/), [signing](https://opentofu.org/docs/v1.13/cli/plugins/signing/), [license](https://github.com/opentofu/opentofu/blob/v1.13.9/LICENSE)

**Deployment and practitioner evidence.** OpenTofu's GA announcement describes a drop-in migration. In a Hacker News discussion, the OpenTofu technical lead describes divergence and points readers to version-specific migration guides. An early-adopter consultancy reports that one migration required no changes to its ordinary Terraform code and describes separate compatibility work on its tooling. These are operator and project accounts with different incentives, covering older releases and specific installations. They support testing registry, API and state compatibility separately. Their scope is the named migrations, with provider and state combinations best verified against the current migration guides and a representative test. [OpenTofu GA announcement](https://opentofu.org/blog/opentofu-is-going-ga/), [Hacker News discussion](https://news.ycombinator.com/item?id=40365198), [Masterpoint field report](https://masterpoint.io/blog/opentofu-early-adopters/)

## Sidecar and portable sandbox options

**Dapr in production.** DataGalaxy reports using Dapr with RabbitMQ to coordinate domains in a cloud-hosted .NET modular monolith. Watts Water reports switching pub/sub providers for some workloads after deploying Dapr. Both are operator accounts published by CNCF, which hosts Dapr. They support the feasibility of a standardized sidecar API and provider substitution in those environments. THESUS's decision turns on whether it needs the same infrastructure portability in its smaller, Windows-first runtime. [DataGalaxy case study](https://www.cncf.io/case-studies/datagalaxy/), [Watts Water case study](https://www.cncf.io/case-studies/wattswatertechnologies/)

**Dapr v1.19.1, Apache-2.0, released 31 October 2026.** `DaprRuntime.initPluggableComponents` calls `pluggable.Discover` and skips initialization on native Windows. On supported hosts, the runtime looks in a socket directory and uses gRPC reflection to discover component APIs, then matches them with a named component spec. `GRPCConnector.Close` cancels its context and closes the connection. The reviewed local socket dialer uses insecure transport credentials, making filesystem access to the socket an important boundary. Component configuration reload has been on by default since v1.18 and closes the old instance before reinitializing the component. Dapr documents temporary unavailability during that interval. The useful transferable pattern is an explicit name, kind and version plus lifecycle-managed transport. For live THESUS browser work, validate and prepare a successor before routing new sessions to it. Drain the original session on its original generation. [Release](https://github.com/dapr/dapr/releases/tag/v1.19.1), [Windows guard](https://github.com/dapr/dapr/blob/v1.19.1/pkg/runtime/runtime.go#L949-L958), [discovery](https://github.com/dapr/dapr/blob/v1.19.1/pkg/components/pluggable/discovery.go#L161), [connector](https://github.com/dapr/dapr/blob/v1.19.1/pkg/components/pluggable/grpc.go#L104-L143), [registration](https://docs.dapr.io/operations/components/pluggable-components-registration/), [reload semantics](https://docs.dapr.io/concepts/components-concept/#hot-reloading), [license](https://github.com/dapr/dapr/blob/v1.19.1/LICENSE)

**Wasmtime v50.0.1, Apache-2.0 with LLVM exception, released 29 October 2026.** WASI 0.3 is the current standard release. Version selection is a host and guest toolchain choice, as the Zed example still targets `wasm32-wasip2`. WIT defines the component boundary. Wasmtime `ResourceLimiter` and `StoreLimitsBuilder` manage selected runtime allocations. Fuel and epochs limit guest execution, with separate timeouts needed for blocking host calls. The 2 October 2026 async-component advisory documents a critical escape path in earlier Wasmtime releases. Use a supported patched runtime, few imports, and an OS boundary for adversarial guests. A practical pilot is an artifact-to-artifact redactor with no network or ambient credentials, fixed memory and deadline, and fixture tests for unsupported interfaces and resource exhaustion. Native Chromium/Playwright and arbitrary Python wheel integrations are poor first candidates. [Wasmtime release](https://github.com/bytecodealliance/wasmtime/releases/tag/v50.0.1), [WASI releases](https://wasi.dev/releases), [runtime limits](https://github.com/bytecodealliance/wasmtime/blob/v50.0.1/crates/wasmtime/src/runtime/limits.rs#L32), [interrupt and host-call behavior](https://docs.wasmtime.dev/api/wasmtime/struct.Config.html#method.epoch_interruption), [security advisory](https://github.com/bytecodealliance/wasmtime/security/advisories/GHSA-32h6-97mm-8q3c), [maintenance policy](https://github.com/bytecodealliance/rfcs/blob/main/accepted/wasmtime-lts.md), [license](https://github.com/bytecodealliance/wasmtime/blob/v50.0.1/LICENSE)

**Zed v1.27.0, released 4 November 2026, is a deployed component-host example.** `WasmHost.load_extension` parses the guest API version, compiles off the UI path, creates a separate store with a `CapabilityGranter`, initializes the guest, and dispatches through its own call loop. `build_wasi_ctx` creates a per-extension working directory and preopens it. Zed distinguishes installed code from working files. Its host capability policies can permit downloads, package installs and command execution, so the effective security properties depend on those grants. For THESUS, use default-deny grants and bounded mailboxes. The Zed extension API crate declares Apache-2.0. Inspect the host file's licensing separately before any source reuse. [Zed release](https://github.com/zed-industries/zed/releases/tag/v1.27.0), [pinned host loader and WASI context](https://github.com/zed-industries/zed/blob/v1.27.0/crates/extension_host/src/wasm_host.rs#L643-L765), [extension authoring](https://zed.dev/docs/extensions/developing-extensions), [capabilities](https://zed.dev/docs/extensions/capabilities), [installation layout](https://zed.dev/docs/extensions/installing-extensions), [extension API package](https://github.com/zed-industries/zed/blob/v1.27.0/crates/extension_api/Cargo.toml#L1-L13)

**A smaller Wasm alternative.** Teppei Fukuda's `go-plugin` v0.9.0, MIT, released 12 March 2025, is a separate design inspired by HashiCorp's implementation. Its generated Go host `GreeterPlugin.Load` creates a wazero runtime, compiles and instantiates an explicitly selected file, and checks its exported API version. `Greet` serializes protobuf through guest linear memory. `Close` releases the runtime on the successful-load path. This is useful implementation evidence for generated guest wrappers and protocol checks. The published example runs guest initialization before its version check. THESUS should verify external manifest compatibility first, bound initialization and test cleanup after rejected artifacts. The Go-specific tooling and older release make this a reference for a narrow design choice. [Release](https://github.com/knqyf263/go-plugin/releases/tag/v0.9.0), [Go WASI support change](https://github.com/knqyf263/go-plugin/pull/71), [generated host](https://github.com/knqyf263/go-plugin/blob/v0.9.0/examples/helloworld/greeting/greet_host.pb.go#L49-L156), [license](https://github.com/knqyf263/go-plugin/blob/v0.9.0/LICENSE)

## Transfer to THESUS

1. **Keep existing seams.** `create_app` already accepts a browser adapter override, owns startup and shutdown, and wires a shared `ControlLockRegistry`. Route the existing fake and Playwright selection through an explicit host-owned factory map while preserving that injection seam and configuration precedence. `BrowserAdapter` is a starting boundary for the local implementation. Its callback and domain objects should stay inside Python. A future worker protocol should carry operation IDs and validated data, with the host owning approval and action execution authority. `LLMProvider` currently supplies model names. Extract a model-call contract when a second implementation needs one. [Composition root](../app/app.py#L32), [browser protocol](../app/integrations/browser/base.py#L12), [model provider seam](../app/agents/llm_provider.py#L6)
2. **Separate install, activation and deletion.** Install a reviewed digest into an immutable package slot. Validate schema, capabilities, effective permission grants and dependency graph before preparing the new instance. Pin the resolved binding to each run. Move the default pointer atomically after readiness. Retain the previous binding for rollback and drain sessions with active leases. Block uninstall while a saved workflow or resumable run still references the implementation. Export or migrate its state before removing it. The host retains an inert audit identity when executable code is removed. Browser profile ownership and in-flight external actions require explicit retirement checks.
3. **Keep the first worker protocol narrow.** A bounded newline-delimited JSON envelope over inherited pipes can exercise `hello`, `invoke`, `cancel` and `shutdown` with one in-flight call per worker. Include a request ID, wire major, deadline and stable result/error envelope. Reserve stdout for frames, drain stderr under size limits, and bound both frame lengths and queue depth. Admit work only after compatible handshake and health check. Cancellation requests can be observed while work runs only if the worker has a responsive control path. Otherwise terminate the worker after a grace period, mark any unresolved external effect `unknown`, and reconcile before retry. Add gRPC when typed cross-language generation, multiplexing or streaming justifies the extra dependency.
4. **Match the boundary to the trust level.** A worker with the user's OS credentials can still access their files and network. Strip inherited environment and handles, pass scoped secret references, and allocate private scratch storage. For a less-trusted integration, use an appropriately configured restricted account, AppContainer, container or VM with tested file, process and egress policy. Windows Job Objects can manage descendants and enforce selected resource limits. Test assignment and cleanup when the host dies, including breakaway and nonstandard child creation paths. Keep profile storage and workspace credentials outside worker permissions. [Microsoft Job Objects](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects), [Microsoft AppContainer isolation](https://learn.microsoft.com/en-us/windows/win32/secauthz/appcontainer-isolation)
5. **Use source as evidence and public contracts as integration surfaces.** Prefer a small adapter or worker around a maintained release, then contribute missing extension points upstream. Independently implement only the documented behavior that THESUS needs and exercise it with shared conformance fixtures. If a fork becomes necessary, record the reason, parent commit, source and artifact licenses, divergence, release cadence and owner. Verify source and binary licensing for the specific distribution before reuse. Keep dependency and state migration tests identical for upstream and fork so the team can move back when the fork's advantage ends.

## Local transport probe

Measured on Windows 11 build 26200, Intel i7-10810U and 64-bit CPython 3.12.14. The probe summed 16 integers and validated every response. It used a 990-byte request for the warm transport test, a preencoded JSON line, synchronous stdio and separate warm worker processes for paired calls. It warmed each worker with 200 calls and ran three batches of 10,000 direct calls, 3,000 warm IPC calls and 1,000 pairs per mode. It ran 50 pairs per mode with independent artificial 10 ms waits and 30 cold samples. Fast-pair concurrency used two threads only to issue blocking pipe calls. Cold time includes Python process launch, one round trip and graceful exit.

| Probe | p50 | p95 |
|---|---:|---:|
| Direct Python call | 0.4–0.5 µs | 0.5–0.6 µs |
| One warm IPC call | 39.0–47.1 µs | 66.5–80.6 µs |
| Two trivial IPC calls sequentially | 79.4–92.6 µs | 127.7–151.2 µs |
| Two trivial IPC calls concurrently | 120.6–132.4 µs | 163.1–176.8 µs |
| Two independent 10 ms waits sequentially | 21.0 ms | 21.7 ms |
| Two independent 10 ms waits concurrently | 10.7 ms | 11.4 ms |
| Cold child, one call, then exit | 76.3 ms | 90.6 ms |

Results establish the tradeoff for these inputs on one host. Sending tiny jobs concurrently added latency, and overlapping independent waits reduced the pair's median by about half. The test excluded client-side request encoding, validation frameworks, production supervision, browser and model latency, memory measurement, security controls, and concurrent traffic. For the implementation spike, measure cold and warm p50/p95/p99, peak memory, queue delay, throughput and cancellation time with production-size payloads. Test single-run and concurrent workloads. Compare same-process, warm-worker and restart-per-call modes on the same host. Reuse a warm worker if the representative workload is startup-sensitive and its reset behavior passes cross-run state leakage tests. Run mutating operations on a shared browser session in lock order regardless of the transport results.
