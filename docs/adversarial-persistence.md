# Persistence and recovery investigation

The tests used the real FastAPI services, temporary SQLite databases and isolated Chromium profiles. Browser cases drove Chromium against loopback fixtures. Scripted planners kept the fault point and intended effect deterministic. The shutdown admission case uses a direct execution manager barrier because it targets the boundary before browser and database teardown.

| Finding | Baseline observation and cause | Correction and evidence |
| --- | --- | --- |
| **P1. Inherited checkpoints drifted forward** | The source checkpoints had `(message, event)` cursors `(1, 1)` and `(2, 3)`. Both inherited copies had `(2, 3)` because the copy routine counted child rows after copying all history. A grandchild created from the earlier inherited checkpoint could receive the later instruction. | Preserve the cursor at each cloned checkpoint and cut the inherited list at the selected checkpoint ID. The nested-fork regression checks the copied cursors and the grandchild's actual message prefix. |
| **P1. A tied timestamp could move an event across the cutoff** | Giving all fixture events the same timestamp and a later snapshot event the smallest UUID made the cutoff include that event and omit an earlier one. The chronological sort key was being used as an append cursor. | Use the append order of the existing SQLite rowid tables for counts, message pagination, event delivery and fork copying. Preserve timestamps separately for Replay. The tied-time regression checks the exact fork history and both cursor directions. |
| **P1. Snapshot fork restored stale browser state** | Chromium moved from `/` to `/details` through a page script. The snapshot recorded the new URL in its browser data alongside the old URL in runtime data. A new fork restored `/` because it consumed the older runtime values. | Update the durable state before writing a new snapshot. The branch reader also prefers the captured state for older snapshots with a live Chromium revision. The regression opens the fork in Chromium and checks `/details`. A snapshot taken with a closed browser keeps the saved URL. |
| **P1. A staged instruction disappeared at a fork** | A user message queued before planning was visible in cloned history. The checkpoint had omitted its pending instruction record, so the fork returned HTTP 409 on Resume. | Save queued instructions with the checkpoint and remap their references to child messages. The fork test resumes through the real worker and verifies that its plan event references the cloned message. |
| **P1. Durable task group could remain idle** | Inject a SQLite-style `OperationalError` in the response read after a successful creation commit. The baseline left both group members queued after a 12-second wait because scheduling depended on the response snapshot. | Dispatch known branch IDs immediately after the commit, before reading the response. The request still reports its read failure. The group reaches settled state in the test without submitting it again or restarting. |
| **P1. Rejected approval could survive without its operation** | Inject `OperationalError` in the `reject` audit write. SQLite rolled back the decision and retained the correlation. The command disappeared from the API because the branch cleared its in-memory proposal before committing the rejection. | Apply in-memory changes after a successful commit under the branch lock. The same approval remains actionable after the simulated rollback and its fixture receives zero POSTs when the rejection succeeds. |
| **P1. A cancelled Release could preserve manual authority** | Cancel the release coroutine just after its SQLite commit. The runtime switched to agent control, but the process kept the old lease because the code had yet to clear it. A real browser command with the revoked lease returned HTTP 200. | Require durable manual mode and user ownership as well as a matching lease under the branch lock. The regression verifies HTTP 409, no request to the fixture, and a fresh lease on the next takeover. |
| **P1. An external effect can precede a failed result write** | Approve a real form and inject `OperationalError` while saving the correlated click event, after the fixture observes one POST. The original restart path already rejected the old approval and reported an unknown outcome. Same-process handling needed to preserve that ambiguity across subsequent work. | Reconcile the durable intent as uncertain. An uncertain checkpoint carries only the operation kind and starts its fork without automatically visiting the last URL. The regression checks one fixture POST, a blank browser in the fork, no automatic GET to the submission URL, and rejection of the old correlation after restart. |
| **P2. Restart retained an obsolete execution owner** | Stop the workspace during a blocked model decision and reopen it. Runtime said `interrupted` while retaining holder `agent` and `pause_requested=false`. The activity log did not record the recovery. | Commit interrupted status, cleared ownership, a pause request, and a recovery event together. The restart test checks the flags and event before any new instruction. |
| **P2. Shutdown still admitted fresh workers** | A worker paused inside cancellation cleanup. While shutdown waited, the scheduler accepted a new worker because it had cleared the task map before closing admission. | Close admission and clear pending reruns under the manager lock. Keep draining workers tracked until they finish. The barrier test exercises both scheduling entry points during shutdown. |
| **P2. Fork replay reordered history** | Forking a mixed message, activity, and checkpoint timeline assigned new timestamps in per-table copy order. Replay grouped messages together and showed later records before earlier checkpoint activity. | Preserve source timestamps. Assign new UUIDs in source order to retain the tie-break for equal timestamps and remap copied references. The test compares the source prefix and fork replay with both ordinary and tied timestamps. |

The common failure mode was a boundary split across distinct systems. Snapshot data and history cursors describe a particular durable cut. In-memory lease and approval updates follow the database commit. An external browser effect and its database record can still fail separately. The intent record makes that case visible and preserves the need for review. SQLite's atomicity covers its database changes, and Python task cancellation can run asynchronous cleanup after a cancellation request. [SQLite atomic commit](https://www.sqlite.org/atomiccommit.html), [Python task cancellation](https://docs.python.org/3.12/library/asyncio-task.html#task-cancellation)

## Checkpoint performance

The fork route loaded the complete event and message histories before slicing to the checkpoint cursors. An early checkpoint has no dependency on the later rows. Push the ordered prefix limit into SQLite while preserving the same branch history and event ordering.

On the Windows verification host, the real fork POST endpoint ran over in-process ASGI with a temporary SQLite database and no browser startup. The fixture seeded 20,000 later messages and 20,000 later events after a checkpoint with one message and one event. Seven measured requests per version returned the expected history. Timing excluded setup, seeding, and verification reads.

| Fork read path | Median | Samples in ms |
| --- | ---: | --- |
| Read full history and slice in Python, matched rerun | 654.36 ms | 720.70, 644.37, 654.36, 659.12, 633.14, 711.36, 650.79 |
| Read the SQLite append-order prefix, matched rerun | 21.29 ms | 22.67, 19.83, 20.62, 21.29, 21.43, 21.18, 22.08 |

The observed median fell by 96.7% in the matched rerun. The initial pre-change and prefix measurements were 767.66 ms and 19.01 ms before the tied-time refinement. A fork with a large retained prefix still copies each retained row. The timed request measures the whole fork operation in this early-cutoff workload.

```powershell
& $workspacePython -m pytest -q tests/test_adversarial_recovery.py
& $workspacePython -m scripts.benchmark_fork --tail-rows 20000 --repeats 7 --full-scan
& $workspacePython -m scripts.benchmark_fork --tail-rows 20000 --repeats 7
```

`--full-scan` recreates the former materialization inside the benchmark. Earlier forks that already imported a wider history retain their stored records. Older checkpoints that predate pending-instruction capture can still require the user to restate an unplanned instruction. SQLite history assumes append-only tables and uses rowid only for relative order at read time. Public cursors remain UUIDs. Destructive external edits, arbitrary database imports, and other storage engines have no tested append-order guarantee. The write-failure tests inject specific faults at known boundaries. Sustained disk outage and power-loss durability remain outside this sample. [SQLite rowid tables](https://sqlite.org/rowidtable.html)
