# Synchronized browser agents and local models

Evidence reviewed November 6, 2026. The workspace synchronizes independent browser tasks at the group level. Creating a group commits its task records together before dispatch. Each member runs in its own browser session and branch, with a workspace-default model or an operator-configured local model profile. Browser capacity governs when queued members can open their sessions, and a shared inference limit governs when they can call their models.

The group publishes a synchronized snapshot of member progress, attention requests, and answers. Clients can wait for a member to need attention or for every member to reach a terminal state. The same branch-level lease, observation revision, and approval rules govern each browser. Each branch has one writer at a time. Members can continue while a sibling awaits approval or manual control, subject to available capacity. [Workspace architecture](../ARCHITECTURE.md)

## Coordination design

| Approach | Fit for this workspace |
| --- | --- |
| Independent browser tasks with a group join | The shipped design suits independently specified tasks such as searching several sites or checking several records. Separate sessions isolate browser state. Group snapshots and wait conditions provide one view of the work. |
| Solo decision loop | The existing mode remains the simplest baseline for one browser task and for comparing quality, latency, and token use. |
| Fixed specialists on one observation | A future option when one task benefits from distinct perspectives. Read-only specialists could check navigation, evidence, or risks against one snapshot. A designated coordinator would join their findings before selecting an action under the existing browser checks. |
| Dynamic delegation or a workflow graph | A future option for tasks with explicit dependencies and dynamic work allocation. LangGraph super-steps offer a useful reference for snapshot, parallel work, and a join. Its interrupt replay semantics also show why action-intent and revision checks must stay authoritative. [LangGraph graph semantics](https://docs.langchain.com/oss/python/langgraph/graph-api) |
| Multiple writers on one tab | Each navigation, form entry, or click can invalidate a sibling's observation. The current design gives independent tasks separate browsers and uses a lease within each branch. |

Anthropic describes independent specialist work and programmatic aggregation as a good fit when the subproblems can be evaluated in parallel. Its production research team reported substantial gains on its internal breadth-heavy research evaluation, alongside substantial token overhead. That system used large hosted models and separate exploration trajectories. Its results provide a design hypothesis and no estimate of this workspace's local-model task success or latency. [Workflow patterns](https://www.anthropic.com/research/building-effective-agents), [production research report](https://www.anthropic.com/research/multi-agent-research-system)

Kim et al. controlled tools and compute across 260 configurations and found performance could improve on decomposable tasks and decline on sequential planning tasks. Cemri et al. found coordination and verification failures across more than 1,600 multi-agent traces. A small local model can make the same mistake in multiple roles, so consensus can repeat errors. These studies used other systems and motivate explicit per-role budgets, one coordinator, and checking the final browser state here. [Agent scaling study, revision 3](https://arxiv.org/abs/2512.08296v3), [multi-agent failure taxonomy, revision 3](https://arxiv.org/abs/2503.13657v3)

The shipped worker runs model inference outside its branch lock, limits simultaneous requests across tasks, and uses cancellation and revision checks to prevent a late output from affecting a redirected or manually controlled browser. A model server may continue work after an HTTP client disconnects, so the branch generation and lease remain the authority. If a later version adds within-task specialists, give them one observation snapshot and short, typed outputs. Treat those outputs and the page as untrusted evidence. The coordinator would still produce at most one validated action per round, and model agreement would leave approval requirements in force. [Python 3.12 cancellation and task groups](https://docs.python.org/3.12/library/asyncio-task.html#task-cancellation), [browser authority and persistence](../ARCHITECTURE.md)

## Runtime behavior and tuning

- **Ollama.** `/api/chat` accepts a JSON schema, a model name, and a per-request `keep_alive`. `/api/tags` lists downloaded models and `/api/ps` shows running models. Names listed by the first endpoint alone give no evidence that multiple models fit resident memory. The server can queue work and evict idle models when a new model does not fit. Documented default per-model concurrency is one. The context allocation grows with parallel sequences, and scheduler source applies architecture-specific single-request limits, including some Qwen multimodal families. Start with one app inference slot and one resident model, then increase capacity after measuring representative runs. Use a finite keep-alive, and avoid alternating large models when the host cannot keep both resident. [Ollama chat and usage metrics](https://docs.ollama.com/api/chat), [local structured outputs](https://docs.ollama.com/capabilities/structured-outputs), [downloaded models](https://docs.ollama.com/api/tags), [residency](https://docs.ollama.com/api/ps), [server concurrency](https://docs.ollama.com/faq#how-does-ollama-handle-concurrent-requests), [scheduler implementation](https://github.com/ollama/ollama/blob/main/server/sched.go)
- **llama.cpp.** A single-model server can share weights across parallel inference slots and continuously batch compatible requests. Its router can place distinct models behind one endpoint, but each loaded child still requires capacity. On a constrained CPU, compare one slot against two slots at the same per-slot context, model, and thread count. For separate role endpoints, budget each model's weights, KV state, runtime overhead, and worker threads. Use loopback endpoints, restrict browser origins, and leave host tools and MCP features off for an inference-only server. The workspace keeps browser tools behind its own API. [llama.cpp b12138 server flags and API](https://github.com/ggml-org/llama.cpp/blob/b12138/tools/server/README.md), [slot and routing internals](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README-dev.md)
- **Queueing and failures.** Client-side admission and deadlines remain useful even with a backend queue. Ollama reports overload as HTTP 503, but open issue reports describe one version queueing requests across different models and a loaded model exceeding the expected queue behavior. These are reported deployment cases, with no reproduction on this host. Separate time spent waiting for application capacity from provider/model latency where possible, and verify memory and queueing after changes. [Cross-model queue report](https://github.com/ollama/ollama/issues/14578), [same-model queue report](https://github.com/ollama/ollama/issues/7758), [reported eviction race](https://github.com/ollama/ollama/issues/17408)

## Model profiles to evaluate

The inspected Windows host had a six-core i7-10810U, Intel UHD graphics, 15.6 GiB installed memory, and 4.4 GiB free at the time of inspection. Cached local weights included Qwen3 0.6B, Qwen3 1.7B Q4_K_M, and Granite 4.2 3B Q4_K_M. Available memory changes with browser and desktop load. The previous Qwen3 1.7B evaluation answered a direct invoice lookup but sought unnecessary approval after navigating the worksheet. Treat it as an installed starting point with known limitations. [Prior local browser evaluation](optimization.md#local-model-smoke-test)

| Profile | Suggested task assignment | Trade-off and verification |
| --- | --- | --- |
| CPU and low headroom | Use one Qwen3 1.7B Q4_K_M endpoint for all group members. Start with one inference slot and short context. | Reuses resident weights and limits memory pressure. Browser tasks can stay active while their model requests wait. Compare group throughput and memory against running the same tasks one by one. [Qwen3 variants](https://ollama.com/library/qwen3/tags) |
| More free RAM, mixed text tasks | Try Granite 4.2 3B Q4_K_M for the more involved tasks and Qwen3 1.7B Q4_K_M for bounded lookups. Compare against assigning the same model to every member. | These are locally cached candidates. Structured output support and weights are documented. Task quality, combined resident memory, and speed remain empirical. [Granite 4.2 variants](https://ollama.com/library/granite4.2/tags), [Qwen3 variants](https://ollama.com/library/qwen3/tags) |
| Dedicated capacity or visual workflow | Test a stronger text profile such as Qwen3 8B, or an installed vision-capable Qwen3.5 model for a task that needs visual evidence. | Send an image only when the task warrants it and the configured provider supports images. Test text versus image and track the backend's actual per-model parallelism. Catalogue sizes describe downloads, while runtime also needs context, runtime buffers, and browser memory. [Qwen3 variants](https://ollama.com/library/qwen3/tags), [Qwen3.5 multimodal variants](https://ollama.com/library/qwen3.5/tags) |

## Local inference capacity check

On the inspected Windows host, I served the same cached Qwen3 1.7B Q4_K_M weights through llama.cpp `b12138` on loopback. I used CPU inference with four threads, reasoning disabled, and 2,048 context tokens per slot. I tested one slot and two slots in that order, restarting and warming the server for each configuration. After one warmup request, four pairs of requests ran concurrently within each pair. Each request supplied a short synthetic invoice observation with a distractor amount and required a schema-constrained JSON object containing the exact total. Prompt-cache reuse was disabled. This measured the provider only, without Chromium or agent coordination.

| Model server slots | Median time to finish both requests | Median individual request | Peak model process working set | Exact totals |
| --- | ---: | ---: | ---: | ---: |
| 1 | 3.524 s | 2.477 s | 2,124.9 MiB | 8/8 |
| 2 | 2.688 s | 2.649 s | 2,350.7 MiB | 8/8 |

Two slots shortened median pair completion by about 24% while adding about 226 MiB to peak model working set. The median individual request took slightly longer. The sample is small and ordered, and both configurations use the same model. This supports trying two slots when a task group generates overlapping short requests and the host has measured memory headroom. Browser task quality, tail latency, and capacity for mixed models require separate measurements.

To repeat the comparison, run `llama-server` with the same GGUF, `--threads 4 --n-gpu-layers 0 --reasoning off`, and either `--parallel 1 --ctx-size 2048` or `--parallel 2 --ctx-size 4096`. Submit two concurrent `/v1/chat/completions` requests after warmup, with unique short observations, `temperature: 0`, `max_completion_tokens: 28`, `cache_prompt: false`, and a JSON schema with a required integer `amount`. Time each HTTP request and the completed pair. Sample server working set while each pair is active. [Server flags and API at b12138](https://github.com/ggml-org/llama.cpp/blob/b12138/tools/server/README.md)

## Workspace evaluation

Compare tasks run individually, a group sharing one model, and a group with models assigned per task. Use identical seeded browser states, the same approval policy, and matched browser action, model token, and wall-time budgets. Include a simple lookup, a multi-step link workflow, missing evidence, misleading page instructions, an interrupted task, and a member that needs attention while another stays active. Score verified final state, task completion, unnecessary approvals, structured output failures, and effects after cancellation. Compare group completion time, task queue delay, tokens per task, first run versus warm runs, and peak process working set. A configuration should preserve zero unapproved effects and improve throughput or quality while keeping interaction responsive. Use separate tasks to tune profiles and to evaluate them. [ToolSandbox stateful evaluation](https://arxiv.org/abs/2408.04682)
