# THESUS modular architecture research

Evidence reviewed November 6, 2026. Scope is the existing local browser workspace, with an extension path for separately deployed capabilities. The immediate decision is how to add and replace planners, tools, and multi-step chains while preserving live browser supervision and durable recovery.

## Decision

Keep the FastAPI process, SQLite repositories, browser owner and execution manager. At app assembly, bind explicit capability IDs to approved implementations. Resolve a workflow into a versioned plan, pin its bindings for the run, and give each node only its inputs and the host-mediated resources it needs. Add one execution boundary for external workers when the first integration requires it. Keep browser effects behind the existing ownership, approval and intent journal.

Start with a second, reversible implementation of a planner or read-only extractor. Compose it with ordinary Python and a small typed workflow definition before committing to a graph framework. The first milestone is an implementation swap and clean removal that changes configuration without requiring edits to the workflow or browser control logic. [Execution design and contracts](modular-execution-design.md), [Roadmap and validation](modularity-validation.md)

## Approaches compared

Assessments below are project-fit judgments. Relative runtime costs follow from the execution boundary. Cross-project timings, memory and maintenance cost were not benchmarked in this study.

| Approach | Modularity, composition and removal | Overhead, interoperability and security | Maturity, effort and long-term fit |
| --- | --- | --- | --- |
| Explicit Python factories with a versioned registry and scoped workflow definitions | Strong separation at typed capability seams. A new binding changes future runs, while removal checks reverse dependencies and pinned runs. A small runner handles bounded branching and joins. | Direct calls share the process and its privileges. Low expected overhead. A schema-defined boundary can later accept other languages. | Uses the shipped architecture and Python primitives. Lowest initial integration effort. THESUS owns the contracts, recovery semantics and compatibility tests. **Adopt first.** |
| Python entry points with a hook manager such as Pluggy or Stevedore | Discovery decouples package release from app release. Hooks suit multi-provider extension points. Discovery or unregister alone cannot remove references, handle durable state or protect active calls. | In-process imports execute package code with host authority. Python packages and dependency constraints must coexist. | Mature patterns. Add allowlisted discovery when independently packaged trusted plugins justify it. Consider a hook library only when a real fan-out extension needs its ordering and result semantics. **Adapt selectively.** |
| Agents SDK or LangGraph behind a capability | SDK handoffs or a graph give richer agent composition. Replaceability remains high if the subgraph exchanges bounded THESUS inputs and outputs. It falls if the main run persists framework types or delegates approval and retries. | Python dependency and checkpoint overhead. Provider and framework state can leak across the seam. Requires mediation for effects, traces and model data. | Maintained implementations with source for run state, interrupts and checkpoints. Good comparative pilots for a specialist or genuinely complex subgraph. **Defer top-level adoption.** |
| Temporal, DBOS or Prefect as workflow runtime | Temporal supplies durable coordination across workers. DBOS is a candidate for Python durability with PostgreSQL. Prefect fits scheduled batch and task orchestration. Moving run histories and in-flight semantics is an explicit migration. | Additional persistence, runtime infrastructure or service configuration. Retry and replay semantics require an external-effect journal and an owning browser worker. | Established and inspectable options with different operating costs. Temporal is the candidate for multi-host execution. Evaluate DBOS for a single-service durability requirement and Prefect for batch, using separate tests. **Adopt only at the matching trigger.** |
| Local process worker with a versioned request protocol | Dependency environments and process lifecycles can differ. Swap workers by generation and drain outstanding requests. Retain durable payload schemas for replay and export. | Serialization, startup, memory and supervision costs. Supports other languages. A same-user subprocess separates crashes and dependencies. Effective containment needs restricted credentials, filesystem, network and resources. | Well-established pattern in Terraform and OpenTofu. A single constrained read-only worker is enough to validate THESUS supervision. **Introduce for the first incompatible or isolated dependency.** |
| MCP tool adapter, remote service or WASI component | Each works at a different boundary. MCP describes tools, a service owns an independently deployed capability, and WASI can constrain a portable compute component. All require explicit local lifecycle and binding rules. | RPC adds network/serialization cost. WASI has a limited host interface and runtime constraints. Discovery metadata is untrusted, and authorization and data handling must remain with THESUS. | Stable standards and working implementations exist, with changing protocol and SDK surfaces. **Pilot narrowly.** Avoid a sidecar, service mesh or WebAssembly runtime until a capability needs one. |
| Full browser-agent framework or maintained fork | Can accelerate autonomous browsing and offer alternative planners. Full-run integration duplicates browser ownership, human intervention and recovery semantics. Removability is poor if the fork defines core state. | A second browser or dispatch path adds resource use and security review. Following divergent API and policy behavior adds maintenance. | Real projects provide reusable ideas and some narrower callable interfaces. **Use a bounded adapter or upstream a narrow patch.** Consider a maintained fork only when the roadmap and security-patch burden are funded. |

## What transfers well

- **Package discovery and composition are separate.** Reuse the discovery convention from Python entry points when needed. Read metadata and verify artifact identity before importing approved code. Resolve dependencies and publish a complete immutable registry snapshot before accepting work. Use explicit injection to keep normal calls reviewable. [Entry point specification](https://packaging.python.org/en/latest/specifications/entry-points/), [Python entry point API](https://docs.python.org/3.12/library/importlib.metadata.html#entry-points)
- **Structured concurrency has a useful scope.** Use `asyncio.TaskGroup` for cancellable siblings that share a fail-fast lifetime. A sibling exception cancels the rest. For independent branches, capture typed failures inside each child and let the join apply its declared policy. Keep browser command draining with the existing owner. [Python 3.12 task groups and cancellation](https://docs.python.org/3.12/library/asyncio-task.html#task-groups)
- **Measure work at the boundary before adding concurrency.** On the local Windows host, the small stdio probe found warm worker calls at 39–47 µs median and cold launch, one call and exit at 76 ms median. Concurrent execution slowed a pair of trivial calls, while it nearly halved the time for two artificial 10 ms waits. These figures isolate the transport and scheduling mechanism. Test browser responsiveness, model throughput and memory independently. [Local transport probe](modularity-plugin-evidence.md#local-transport-probe)
- **Durable coordination and side effects have separate outcomes.** Commit an intent before dispatch. Carry a stable operation identity across attempts and use provider idempotency only where the provider contract proves its scope. Reconcile ambiguous effects before any repeat. If an external event publisher becomes necessary, an outbox can couple an event to its database update. Delivery can repeat, so consumers still need deduplication. [THESUS failure reproduction](adversarial-persistence.md#persistence-and-recovery-investigation), [AWS transactional outbox design](https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/transactional-outbox.html)
- **Protocols make good edges.** Use JSON Schema 2020-12 for external contracts. A THESUS MCP adapter should bind a particular server identity, protocol revision, tool and reviewed schema digest. MCP tool descriptions and annotations can inform a model, while local policy classifies effects and authorizes calls. Treat discovery changes as a new reviewed binding and scope tool metadata caches to the appropriate identity and authorization. The MCP project lists 2026-07-28 as current at review time. That revision uses per-request protocol metadata and optional advance discovery with `server/discover`. The older 2025-11-25 revision uses an initialization handshake. Pin and test each enabled revision explicitly, including handling of interim input requests before enabling them. [JSON Schema specification](https://json-schema.org/draft/2020-12), [MCP versioning](https://modelcontextprotocol.io/specification/versioning), [MCP changelog](https://modelcontextprotocol.io/specification/2026-07-28/changelog), [MCP tools](https://modelcontextprotocol.io/specification/2026-07-28/server/tools)
- **Keep telemetry and audit separate.** Trace node execution and propagate standard context at worker boundaries. Preserve approval, intent, outcome and configuration provenance as durable application records even when telemetry is sampled or unavailable. Keep raw goals, page text, cookies, credentials and model payloads outside default trace attributes. [OpenTelemetry trace API](https://opentelemetry.io/docs/specs/otel/trace/api/), [OpenTelemetry context propagation](https://opentelemetry.io/docs/specs/otel/context/api-propagators/)

## Decision triggers

| Finding in a representative test | Next decision |
| --- | --- |
| A configured implementation swap and clean removal work with built-in factories | Keep factories. Add independent package discovery when a real external package release requires it. |
| Two required plugins cannot share a Python environment, or a plugin needs a smaller trust boundary | Compare a restricted local worker with a service or a narrow WASI capability. Adopt the first boundary that passes isolation, fault and resource tests. |
| A real workflow needs repeated dynamic planning or subgraph features that outgrow bounded composition | Compare the local executor and a wrapped LangGraph subgraph using the same recorded inputs and fault points. Keep the browser effect gateway in both. |
| Requirements call for cross-host failover, durable timers or resumed workflows after machine loss | Compare Temporal against a simpler operating model, including DBOS where appropriate. Pilot read-only jobs and preserve the existing run owner during migration. |
| One host misses latency or throughput targets | Profile browser memory, inference queuing and SQLite contention independently. Add capacity at the measured bottleneck. The existing local measurements point to browser memory and model slots as constraints worth testing first. [Workspace measurements](optimization.md#measured-workspace-performance), [Local model capacity](multitask-research.md#local-inference-capacity-check) |

## Evidence scope

Local findings come from source inspection and the workspace's recorded tests and measurements. External behavior is tied to pinned code or official documentation in the companion reports. Maintainer case studies and community discussions supply operating examples and test hypotheses. GitHub API limits prevented exhaustive fork-tree discovery, and the indexed X material supplied no corroborated technical evidence. Release dates establish activity. Security, compatibility and support require separate checks. The design and its acceptance thresholds are proposals. End-to-end performance, fault behavior, compatibility across boundaries and cleanup remain gates for the staged experiments.
