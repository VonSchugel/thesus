# Browser infrastructure and shared control research

Reviewed 5 November 2026. The baseline already had FastAPI, async SQLite, a Jinja workspace, a branch-specific browser-use session, and persisted control and replay events. The default fake adapter made the existing control tests deterministic. The real adapter returned URL and tab metadata, and its snapshot returned metadata alone. Its browser-use callback inspected the first action in a model action list. Approving that action could invoke a new model step with the callback disabled. A safe real viewport needed an input path through the application’s ownership checks and a dispatcher capable of running the exact action that was approved. The work preserves the existing session, database, event, and checkpoint layer, and provides those capabilities in the Chromium backend. [Baseline browser adapter](../app/integrations/browser/browser_use_adapter.py), [baseline control lock](../app/core/control_lock.py), [Chromium adapter](../app/integrations/browser/playwright_adapter.py).

## Candidate inspection

### Playwright and Chromium DevTools Protocol

Playwright supplies a persistent context with an app-owned user-data directory, typed tab, pointer, keyboard, and file primitives, and screenshot masking. The persistent context’s closure also closes its launched browser. Local launch uses the Playwright protocol and a private driver channel. Attaching to externally launched Chromium using `connect_over_cdp` is available but the maintainers document reduced fidelity relative to the Playwright connection. Chromium CDP complements the typed API with an accessibility-tree read and an optional visual pipeline. BrowserType launch options default to disabling Chromium’s sandbox unless `chromium_sandbox` is explicitly enabled. The workspace enables it by default. [BrowserType API](https://playwright.dev/python/docs/api/class-browsertype), [screenshot API](https://playwright.dev/python/docs/api/class-page#page-screenshot), [Playwright Apache-2.0 license](https://github.com/microsoft/playwright/blob/2344315c542af22002c132567b5a66464e7f4db6/LICENSE), [CDP accessibility](https://chromedevtools.github.io/devtools-protocol/tot/Accessibility/#method-getFullAXTree).

`Page.startScreencast` supplies experimental target-level JPEG/PNG events and dimensions. The client acknowledges every frame ID and must manage tab replacement, visibility, and resize races. Chromium DevTools’ viewer uses capture metadata for zoom and input mapping. Browser and frontend processes should discard superseded frames and keep cursor, viewport, and tab metadata coupled. Playwright’s own screenshot queue had a renderer-hang timeout bug reported July 2025. The June 2026 fix races screenshot cleanup against the timeout. Separate frame requests from command admission and keep a capture deadline even with that fix. [CDP screencast definition](https://chromedevtools.github.io/devtools-protocol/tot/Page/#method-startScreencast), [DevTools viewer source](https://chromium.googlesource.com/devtools/devtools-frontend/+/a6e6344c2ad021c594e2962d61db87621a2f8987/front_end/screencast/ScreencastView.ts), [Playwright #36702](https://github.com/microsoft/playwright/issues/36702), [timeout fix #40901](https://github.com/microsoft/playwright/pull/40901).

CDP can read authentication state and invoke privileged browser commands. Chrome documented cookie theft using debugging access and changed the default-profile behavior in Chrome 136. An independently authored security study reproduced abuse of CDP exposed via an extension. The workspace uses an isolated profile and keeps debugging access server-side. Playwright’s request routing has a separate limitation. A redirect can escape interception after its first URL. The adapter pairs request filtering with an authenticated loopback forward proxy that evaluates HTTP and CONNECT destinations and pins the upstream IP used to open the socket. This reduces redirect and DNS-rebinding exposure for proxied requests. Deployment-level egress restrictions are still required for an untrusted, multi-tenant environment. [Chrome security note, March 2025](https://developer.chrome.com/blog/remote-debugging-port), [Chrowned by an Extension, 2023](https://arxiv.org/abs/2305.11506), [Playwright redirect issue #34994](https://github.com/microsoft/playwright/issues/34994), [workspace egress proxy](../app/integrations/browser/egress_proxy.py).

### Steel, Browserbase and Browserless

- **Steel Browser.** Cloned and inspected Apache-2.0 `d86cc799` (3 November 2026). The socket handler attaches to a Puppeteer target, forwards validated protocol-shaped keyboard and mouse commands, tracks page closure, and subscribes to a shared per-page screencast. The screencast module acknowledges every frame, supports binary output and can request a settled frame. Its test asserts acknowledgement and cleanup behavior. This is a practical pattern for a later push-based implementation. Steel’s cloud viewer can be interactive or read-only and the docs treat debug URLs as bearer access. The public self-hosting tracker has reports of stale session route selection (#333), iOS keyboard limitations (#270), and an API exit during rapid release (#329). These are issue reports with specific repro conditions and do not establish cloud behavior or failure rates. The examined commit includes an upstream dependency security update (#418). Use the project as a reference or evaluate it as an external browser worker with application-controlled input. [Casting handler](https://github.com/steel-dev/steel-browser/blob/d86cc79917f53e00c7158cd639781b944354d06c/api/src/plugins/browser-socket/casting.handler.ts), [shared screencast source](https://github.com/steel-dev/steel-browser/blob/d86cc79917f53e00c7158cd639781b944354d06c/api/src/plugins/browser-socket/page-screencast.ts), [license](https://github.com/steel-dev/steel-browser/blob/d86cc79917f53e00c7158cd639781b944354d06c/LICENSE), [viewer permissions](https://docs.steel.dev/overview/sessions-api/configuration), [#333](https://github.com/steel-dev/steel-browser/issues/333), [#270](https://github.com/steel-dev/steel-browser/issues/270), [#329](https://github.com/steel-dev/steel-browser/issues/329), [#418](https://github.com/steel-dev/steel-browser/pull/418).
- **Browserbase.** Its documented debug response contains a session view and per-tab viewer URLs. The viewer can watch, click, type, scroll, and handle enabled uploads. It provides a clear example of switching the displayed page when a new remote tab appears. The Python SDK is Apache-2.0 at reviewed revision `d684100d` (4 November 2026). The cloud infrastructure and viewer server are a hosted service. The public SDK and provider docs establish the interface, with no independent inspection of the renderer, end-to-end latency, or tenant isolation. A vendor iframe would require a revocable input path synchronized with our lease before it could be interactive. [Live View and tabs](https://docs.browserbase.com/platform/browser/observability/session-live-view), [SDK debug resource](https://github.com/browserbase/sdk-python/blob/d684100d27a44383313e9a67496bf32e4aceb236/src/browserbase/resources/sessions/sessions.py), [SDK license](https://github.com/browserbase/sdk-python/blob/d684100d27a44383313e9a67496bf32e4aceb236/LICENSE), [provider engineering overview](https://www.browserbase.com/blog/what-is-a-browserbase-browser).
- **Browserless.** Cloned and inspected `b4e6239e` (4 November 2026). The Playwright browser bridge’s configuration and server code implement wire-frame handling and URL guards. The hosted CDP extensions document temporary viewer IDs, optional read-only mode, tab controls, and a choice to keep the viewer connection alive independently. Its licensing is SSPL-1.0 or a commercial license. Availability of hosted CDP features in a specific self-hosted distribution requires a separate test and licensing review. The public bridge and changelog show that proxy guards, Playwright version alignment, and idempotent CDP shutdown require ongoing work. [Wire bridge](https://github.com/browserless/browserless/blob/b4e6239e734dc4207d0d8dcfa3e5823085729aa9/src/browsers/browsers.playwright.ts), [license](https://github.com/browserless/browserless/blob/b4e6239e734dc4207d0d8dcfa3e5823085729aa9/LICENSE), [changelog](https://github.com/browserless/browserless/blob/b4e6239e734dc4207d0d8dcfa3e5823085729aa9/CHANGELOG.md), [Live URL CDP API](https://docs.browserless.io/api-reference/cdp-extensions), [embed guide](https://docs.browserless.io/baas/monitor-sessions/embedding-live-url).

### Remote desktop and WebRTC

- **noVNC and related forks.** Cloned and inspected `e8b5024d` (23 October 2026). The browser client renders RFB display updates, forwards keyboard and pointer input, and supports scale-to-fit and a view-only mode. Core JavaScript is MPL-2.0 and assets have separate terms. `viewOnly` checks in the client are valuable feedback and need a server-side capability boundary to prevent forged input. Upstream #1799 describes missing key-up events when the host OS captures shortcuts, relevant to remote modifier state. The `volcengine/novnc` embedding fork adds a host messaging bridge and Apple keyboard adaptations, explicitly as a published snapshot with upstream CI removed. The `ngxson/novnc-webrtc` experiment moves transport to WebRTC. The inspected revision `8a75e771` is from September 2023. Retain the focus and key-release lessons and evaluate a maintained desktop stack only if a workflow needs native dialogs or browser chrome. [noVNC implementation](https://github.com/novnc/noVNC/blob/e8b5024d4603587b29ffede4fbd28b1fa2939829/core/rfb.js), [licenses](https://github.com/novnc/noVNC/blob/e8b5024d4603587b29ffede4fbd28b1fa2939829/LICENSE.txt), [shortcut issue #1799](https://github.com/novnc/noVNC/issues/1799), [embedding fork](https://github.com/volcengine/novnc), [WebRTC fork](https://github.com/ngxson/novnc-webrtc/tree/8a75e7719bfd2532f45b6d90d74e12e8ca7496ab).
- **n.eko.** Cloned and inspected Apache-2.0 `22e35dd5` (28 October 2026). The WebSocket handler checks the user’s host permission and current control state. The WebRTC manager creates peer connections and capture code streams a desktop, with an HTTP JPEG fallback described in the docs. The reviewed commit rejects cross-origin WebSocket handshakes when CORS configuration is empty. This offers a credible comparison for desktop-level control, with additional GStreamer and container operations. ICE and TURN setup, audio/video codec handling, and desktop-scoped privacy make it a larger first deployment. A server-side host permission is reusable as a concept, while an agent still needs the application’s own command boundary. [Control handlers](https://github.com/m1k1o/neko/blob/22e35dd52560acc4c17522b029c215c5cc6e14de/server/internal/websocket/handler/control.go), [WebRTC manager](https://github.com/m1k1o/neko/blob/22e35dd52560acc4c17522b029c215c5cc6e14de/server/internal/webrtc/manager.go), [capture docs](https://neko.m1k1o.net/docs/v3/configuration/capture), [reviewed revision and license](https://github.com/m1k1o/neko/tree/22e35dd52560acc4c17522b029c215c5cc6e14de), [W3C WebRTC recommendation, March 2025](https://www.w3.org/TR/2025/REC-webrtc-20250313/).

## Evaluation

Scores range from 1 (poor fit) to 5 (strong fit) for the existing local project. Security and human control get double weight because display capability without a server-enforced action boundary would fail the central requirement. Scores estimate fit and integration effort. Only the local capture paths were benchmarked.

| Candidate | Function | Architecture | Performance | Reliability | Human control ×2 | Integration | Maintenance | Security ×2 | License | Effort | Score / 60 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| Playwright JPEG + server commands + AX | 4 | 5 | 3 | 4 | 5 | 5 | 5 | 4 | 5 | 5 | 54 |
| CDP screencast + same command gate + AX | 4 | 5 | 5 | 3 | 5 | 4 | 4 | 4 | 5 | 3 | 51 |
| Steel self-hosted | 5 | 4 | 4 | 3 | 3 | 3 | 4 | 3 | 5 | 3 | 43 |
| Browserbase / Browserless hosted | 5 | 4 | 4 | 4 | 3 | 3 | 4 | 3 | 2 | 3 | 41 |
| n.eko WebRTC desktop | 4 | 3 | 4 | 3 | 3 | 2 | 4 | 3 | 5 | 2 | 39 |
| noVNC + private VNC container | 4 | 3 | 3 | 4 | 3 | 2 | 4 | 3 | 4 | 2 | 38 |
| DOM reconstruction as display | 2 | 3 | 4 | 2 | 2 | 3 | 2 | 2 | 5 | 1 | 30 |

Playwright screenshot capture is a low-cost local fit and supports a targeted password-field mask. The selected pipeline uses real Chromium pixels as the visual authority, with bounded DOM target and AX observations for model grounding. DOM reconstruction would lose rendering of canvas, video, cross-origin frames and browser widgets, and would make sanitized replicas a second source of UI state. The local pipeline displays the active tab and retains per-tab IDs within the running context. Local scaling maps clicks back to the frame’s CSS coordinates. Browser profiles may recover login state and the app can reopen the last safe address. Native dialogs, audio, and full desktop fidelity would require an alternate capture strategy. A managed service would add per-session operating cost, external credentials, session limits, and data handling review. Current vendor prices were outside the project’s selection criteria and were not used.

The primary workspace keeps the browser and its current owner visible. Chat and event history sit beside it, with state-specific buttons and approval context. A fullscreen viewer maximizes page area, but switching away from the task panel makes intervention slower. An independent window works for desktop workflows, with weaker discoverability and more opportunities to send input without the app’s control gate. The workspace follows the live viewer and DevTools pattern of a selected tab with explicit input focus. It separates pause from input takeover, keeps the final destination near controls, and maps visual input through the same server that checks ownership. Interaction-Driven Browsing uses a prototype and qualitative workflow analysis to motivate inspectable intervention. It does not validate this layout or provide task-success data for the current environment. [Browserbase Live View](https://docs.browserbase.com/platform/browser/observability/session-live-view), [DevTools viewer implementation](https://chromium.googlesource.com/devtools/devtools-frontend/+/a6e6344c2ad021c594e2962d61db87621a2f8987/front_end/screencast/ScreencastView.ts), [Interaction-Driven Browsing, September 2025](https://arxiv.org/abs/2509.12049).

Use an HTTP mutation channel for input, a replayable event channel for authoritative state, and a separate replaceable capture channel. SSE gives a browser reconnect cursor with `Last-Event-ID` and fits one-way execution events. The server needs its own replay semantics and ordering independent of the transport. Binary WebSockets fit a future push-based viewport and high-frequency pointer stream, with explicit backpressure and reconnect state. WebRTC data channels make sense if a video connection already exists. They would still need ordered command handling and independent persistence for workflow events. [WHATWG Server-Sent Events](https://html.spec.whatwg.org/multipage/server-sent-events.html), [IETF WebSocket protocol](https://www.rfc-editor.org/rfc/rfc6455), [W3C WebRTC data channels](https://www.w3.org/TR/webrtc/#peer-to-peer-data-api).

## Local capture experiment

Windows with Intel i7-10810U, Node 24.14.0, Playwright Node 1.58.2 and bundled headless Chromium 145.0.7632.6, sandbox enabled. A local static HTML document used a heading and a continuously animated repeating gradient covering roughly 80% of a 1280 × 800 CSS viewport at DPR 1. Capture used JPEG quality 70. Each case ran for three alternating 4.5-second trials. Pull was scheduled every 125 ms with one capture in flight. Push used target-level CDP, immediate acknowledgements, and `everyNthFrame=1` or `8`.

| Capture | Effective fps | p95 local timing | JPEG payload rate, decimal MB/s |
| --- | ---: | ---: | ---: |
| Screenshot pull, uncapped comparison series | 7.08–7.54 | 58.7–67.7 ms request to JPEG | 0.93–1.00 |
| CDP push, every frame | 59.55–59.88 | 16.9–17.6 ms compositor timestamp to Node callback | 7.80–7.84 |
| Screenshot pull, matched comparison series | 7.47–7.65 | 45.4–51.3 ms request to JPEG | 0.98–1.00 |
| CDP push, every eighth frame | 7.30–7.32 | 15.0–19.5 ms compositor timestamp to Node callback | 0.95–0.96 |

To reproduce, launch Chromium with `chromium.launch({headless: true, chromiumSandbox: true})`, create the viewport above, and use `page.setContent` with a 700 ms CSS animation that advances a repeating gradient’s background position. Use `page.screenshot({type:'jpeg', quality:70, timeout:2000})` and time with `performance.now()`. Compare to `Page.startScreencast` with `format:'jpeg',quality:70,maxWidth:1280,maxHeight:800,everyNthFrame:1` or `8`. For each `Page.screencastFrame`, count `Buffer.byteLength(event.data,'base64')`, record `Date.now()-event.metadata.timestamp*1000`, and acknowledge `event.sessionId`. Divide frame counts and JPEG bytes by wall time. The timestamp intervals differ and should not be compared as end-to-end latency. JPEG payload excludes HTTP and CDP framing, base64 inflation, TCP, decoding, and browser paint. This experiment did not measure process CPU/RSS or model token usage and the repository backend pins a later Playwright version. Static pages, dashboard repaint rates, fonts, and video will give different results.

The app uses a short latest-frame cache and samples only while viewers ask for frames. Uncapped push costs substantially more bandwidth for this motion case. At comparable frame rates, the two JPEG rates overlap, so bandwidth does not choose the architecture by itself. Revisit capped CDP push if representative human interactions exceed the target of 500 ms p95 from input to fresh visible frame on a local connection or if capture CPU becomes a bottleneck. Compare 5–8 fps pull and capped push at identical quality and dimensions across an idle page, a form, and a highly animated page. Record input acknowledgement, visible update, browser/backend CPU and RSS, aggregate viewer bandwidth, and whether takeover plus resume still succeeds. Independent published screen-sharing experiments motivate testing under packet loss as well as loopback, but their endpoints and native clients differ from the workspace. [Huang et al., ACM TOMM performance study](https://people.cs.nycu.edu.tw/~chuang/pubs/pdf/2021tomm.pdf).

A separate Python adapter smoke check with sandboxed Chromium verified JPEG capture, bounded AX with a password value omitted, a typed field edit, rejection of an older browser revision, file staging and retrieval, link navigation, tab creation and closure, and viewport resize. An allowed local fixture issued an HTTP redirect to an ungranted loopback port, and the second origin observed zero requests. A subsequent public HTTPS navigation completed through the proxy with the expected page title. One Windows run emitted an asyncio connection-reset callback during transport cleanup and exited successfully. [Automated browser fixture and integration cases](../tests/test_browser_workspace.py).

## Community evidence and limits

The December 2024 Steel Show HN describes operational costs of maintaining Chrome, session tooling, and observability from Steel’s authors. The April 2025 Browserable Show HN describes provider portability and the authors’ work on reliability. Both are maintainer reports. A December 2024 Reddit thread describes trouble forwarding base64 screencast frames across distributed infrastructure and a later preference for KasmVNC for desktop sessions and Steel for headless sessions. It gives practical leads with no reproducible timings. The local capture experiment independently shows why encoding and frame caps matter under motion. [Steel Show HN](https://news.ycombinator.com/item?id=42245573), [Browserable Show HN](https://news.ycombinator.com/item?id=43641370), [Reddit WebRTC discussion](https://www.reddit.com/r/WebRTC/comments/1hft1p7/).

X searches did not yield an accessible primary thread with enough technical detail to support a decision. GitHub’s unauthenticated API rate-limited later tree requests. Direct clones of Steel, Browserless, noVNC, and n.eko supplied the source evidence. Public issue and PR inspection was targeted to display, teardown, security, and keyboard paths. Hosted implementations, private roadmap discussion, WAN performance, and feature-specific vendor costs were outside the verified evidence. No vendor-specific code was copied into the workspace.
